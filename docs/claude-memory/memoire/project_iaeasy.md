Projet créé 2026-07-07, séparé de ConfIA : outil académique pour apprendre l'IA en la manipulant — catalogue de modèles, module d'entraînement en direct avec courbe de loss, et un parcours qui débloque progressivement 5 briques (LLM seul → RAG → Outil/MCP → Agent unique → Multi-agent), plus un constructeur d'architecture en mode "architecte".

**Repo** : `https://github.com/adilinfo14/iaeasy.git` (poussé, dernier commit "v3" le 2026-07-08). **Dev/déploiement** : directement sur `confia-vm` dans `/home/adil/iaeasy` (mêmes conventions que [[project_confia]]).

**Stack** : FastAPI (backend, sert aussi le build React statique depuis `/static`) + React/Vite/TS + `@xyflow/react` (canvas) + recharts (courbes/graphiques). Un seul conteneur `iaeasy`, réseau externe `proxy-net`, réutilise le conteneur `ollama` déjà présent sur le homelab (`OLLAMA_URL=http://ollama:11434`).

**Infra dev** : `docker-compose.yml` bind-monte `./backend/app:/app/app:ro`, et le `Dockerfile` lance uvicorn avec `--reload` — un simple `tar czf ... | ssh confia-vm 'tar xzf ...'` suffit pour déployer un changement de code backend (pas besoin de rebuild Docker). Un rebuild complet (~5-10 min) n'est nécessaire que si `backend/requirements.txt` ou `frontend/` changent.

**v2 (2026-07-08), suite à un retour détaillé de l'utilisateur jugeant la v1 "trop basique"** :
- **Catalogue** : passé de 10 à **19 modèles / 7 à 15 familles**. Nouveaux : CamemBERT NER, CamemBERT QA (extractif), T5 résumé FR, YOLOv8 classification, Whisper tiny (transcription), Isolation Forest fraude bancaire, régression logistique scoring crédit, NMF recommandation, Mxbai Embed (comparatif à Nomic). Chaque modèle a plusieurs `exemples` (pas un seul input fixe) et un rendu de résultat riche typé (`ResultRenderer.tsx` : graphiques recharts, image annotée en base64, lecteur audio, jauges de confiance, entités surlignées) au lieu du JSON brut.
- **Entraînement** : passé d'un seul scénario (sentiment CamemBERT) à **3 scénarios** couvrant 2 familles d'algo (deep learning vs classique) : spam (régression logistique/TF-IDF, quasi-instantané) et prévision de CA (régression linéaire par descente de gradient codée à la main). Chaque scénario affiche l'aperçu réel des données AVANT de lancer, et permet de **tester le modèle fraîchement entraîné** avec sa propre entrée juste après (endpoint `/training/{job_id}/tester`).
- **Parcours** : réécrit en narratif — chaque brique a `mise_en_situation`/`avant`/`apres` (histoire d'un développeur chez un artisan du bâtiment), et l'utilisateur tape ses propres questions/expressions à chaque étape au lieu d'exemples figés (y compris ajouter sa propre ligne au corpus RAG).
- **Constructeur** : devenu un vrai "mode architecte" — 9 composants granulaires (`source_document`, `chunking`, `base_vectorielle`, `llm_agent`, etc., voir `agents/architecture.py`) au lieu des 5 briques pédagogiques seules, **3 templates prêts à charger** (Assistant RAG documentaire, Agent avec outils, Pipeline multi-agent) qui posent un graphe complet en un clic, et un **inspecteur d'artefact par nœud** (`resultats_par_noeud` renvoyé par `/agents/run`, cliquer un nœud affiche ce qu'il a produit — chunks, passages retrouvés, etc.).
- **Ergonomie** : nouvelle page d'accueil (`Accueil.tsx`) avec 4 cartes de modules + badge de progression, transitions/hover sur les cartes et boutons.

**Fix instabilité entraînement sentiment (2026-07-08)** : le taux d'apprentissage par défaut du `Trainer` (5e-5) était trop élevé pour ~20 étapes sur 40 exemples — la tête de classification (initialisée aléatoirement) partait dans une mauvaise direction dès les premiers pas et le modèle "s'effondrait" vers une seule classe (loss oscillant 0.55-0.9, avis clairement positifs classés négatif après entraînement — repéré par l'utilisateur via un screenshot du résultat réel, pas anticipé en test). Fix vérifié sur 2 runs identiques (10/10 correct, loss descend proprement 0.76→0.50) : `learning_rate=2e-5`, `warmup_ratio=0.1`, `max_grad_norm=1.0`, `seed=42` (reproductibilité), `num_train_epochs` passé de 4 à 10 pour laisser converger à ce taux plus bas. **Leçon** : toujours faire tourner un scénario d'entraînement plusieurs fois et vérifier les prédictions sur des exemples au sens non-ambigu avant de le considérer fiable — un backend qui répond 200 OK ne garantit pas que le modèle a réellement bien appris.

**Pièges dépendances Python (transformers 5.13 + torch 2.12 CPU)** :
- `sentencepiece` ET `protobuf` sont TOUS LES DEUX nécessaires pour charger un tokenizer SentencePiece (CamemBERT) — sans `protobuf`, extraction cassée (`Error parsing line b'\x0e'`).
- Le binding Python officiel de `fasttext` est incompatible avec numpy>=2 — utiliser **py3langid** à la place.
- Les tasks génériques `"translation"` et `"question-answering"` du pipeline `transformers` ont été retirés dans les versions récentes — appeler directement `AutoModelForSeq2SeqLM`/`AutoModelForQuestionAnswering` + tokenizer.
- Le tokenizer BARThez (`moussaKam/barthez-orangesum-abstract`) est cassé avec cette version de `tokenizers` (bug amont réel, `argument 'vocab': 'dict' object cannot be converted to 'Sequence'`, même en `use_fast=False`) — remplacé par `plguillou/t5-base-fr-sum-cnndm` (préfixer `"summarize: "`).
- `ChronosBoltPipeline.predict_quantiles()` attend le kwarg `inputs=`, pas `context=`.
- **`torchcodec` casse silencieusement tout le pipeline audio de `transformers`** : sa simple présence (même si sa lib native ne charge pas, faute de FFmpeg) fait que `transformers` tente un `import torchcodec` inconditionnel dans le pipeline ASR et plante — NE PAS installer `torchcodec`. Pour charger un échantillon audio HF sans lui : `dataset.cast_column("audio", Audio(decode=False))` puis décoder soi-même les `bytes` avec `soundfile.read(io.BytesIO(...))`.
- Sur CPU pur, un appel Ollama sans `options.num_predict` peut mettre plusieurs minutes pour un modèle 7B — toujours plafonner (300 tokens ici).

**Bug majeur corrigé — config des nœuds jamais envoyée (2026-07-08)** : dans `BrickCanvas.tsx`, `executer()` envoyait systématiquement `config: {}` pour chaque nœud, quel que soit l'exemple chargé depuis un template — chaque nœud tournait donc avec les valeurs de repli codées en dur du backend, jamais avec le prompt réellement sélectionné. Symptôme signalé par l'utilisateur : impossible de voir/fournir l'entrée d'un nœud avant exécution. Fix : les nœuds portent leur `config` réelle (avec aperçu tronqué affiché directement sur le nœud), un nouveau champ `champs_config` par composant (`architecture.py`) pilote un formulaire éditable (textarea/texte/nombre/select) dans le panneau de détail du Constructeur, relié au canvas via `forwardRef`/`useImperativeHandle` (`BrickCanvasHandle.modifierConfigNoeud`). Les valeurs par défaut des select (modèle, modele_a/b, outil) sont alignées explicitement sur les fallbacks réels du backend pour qu'il n'y ait jamais d'écart affiché/exécuté. **Leçon** : quand un payload passé à l'exécution est construit séparément de l'état affiché, toujours vérifier que les deux sources ne divergent pas silencieusement.

**Durcissement sécurité (2026-07-08, demande explicite "sécurise au max")** : app publique sans authentification, donc chaque endpoint est un vecteur d'abus potentiel.
- **Le plus critique** : `/api/agents/run` acceptait un `modele`/`modele_a`/`modele_b` arbitraire dans le config JSON — sans liste blanche, un appel direct pouvait forcer l'Ollama partagé du homelab à charger le 70B volontairement exclu ailleurs, dégradant tous les autres services du serveur (pas seulement iaeasy). Fix : `_MODELES_AUTORISES` dans `engine.py`, retombe sur le défaut si hors liste.
- Calculatrice (`tools.py`, AST whitelist) ne bornait ni la magnitude des nombres ni l'exposant — un `9**999999999` aurait gelé le process Python mono-worker (uvicorn sans `--workers`) pour **tous** les visiteurs simultanément, pas juste l'auteur. Bornes ajoutées : |x| ≤ 10^12, exposant ≤ 64, expression ≤ 200 caractères.
- `/api/training/start` n'avait aucune limite de concurrence : spammable pour lancer un nombre illimité de fine-tunings CPU réels (thread par job) + le dict `_jobs` grossissait indéfiniment en mémoire. Fix : max 3 jobs `en_cours` simultanés, éviction FIFO au-delà de 100 jobs conservés.
- Graphe `/api/agents/run` sans plafond de taille (chaque nœud peut déclencher plusieurs appels Ollama) → plafond 20 nœuds/40 arêtes, à la fois Pydantic (422) et engine.py (défense en profondeur).
- Champs texte libres sans `max_length` partout (`input_text`, `entree`, `visiteur_id`, `brique_id`, `prompt`/`texte` en config JSON libre) → longueurs max ajoutées ; `visiteur_id`/`brique_id` aussi cappés côté store (taille max du set) contre un remplissage disque scripté.
- CORS `allow_origins=["*"]` → restreint au domaine de prod (sans risque : le SPA est servi en same-origin par le même process, donc aucun impact fonctionnel). `/docs`, `/redoc`, `/openapi.json` désactivés (`docs_url=None` etc.) — tombent proprement sur le catch-all SPA au lieu de fuiter le schéma API.
- **nginx** (config vécue seulement dans le conteneur `proxy-nginx`, PAS dans le repo git — pattern déjà connu pour les autres apps) : `limit_req_zone` général (10r/s) + zone stricte dédiée aux endpoints coûteux (`/api/agents/run`, `/api/training/start`, `/api/catalogue/*/essayer`, 6r/min avec `limit_req_status 429`), `client_max_body_size` réduit de 20M à 2M (aucun upload de fichier sur ce site), CSP + Permissions-Policy ajoutés en plus des headers déjà présents (HSTS, X-Content-Type-Options, X-Frame-Options, Referrer-Policy).
- `docker-compose.yml` : `cap_drop: [ALL]` + `security_opt: [no-new-privileges:true]` — testé sans casser le démarrage (le conteneur n'a besoin d'aucune capability Linux spéciale).
- Tout revérifié en conditions réelles post-déploiement : modèle hors liste → fallback silencieux confirmé, calcul dangereux → rejeté proprement (pas de gel), 4e entraînement concurrent → 400 explicite, `/docs` → sert le SPA et non plus Swagger.
- **Non fait / hors scope de cette passe** : conteneur tourne toujours en root (cap_drop appliqué à la place — migration vers un user non-root nécessiterait de gérer la permission du volume nommé `iaeasy_data` déjà peuplé par root, risque de casse à tester en local avant de le faire sur un site déjà en prod).

**5 modules d'accessibilité IA (2026-07-08, suite à "propose-moi 10 idées pour rendre l'IA plus accessible")** : glossaire (29 termes + composant `<Terme>` cliquable), fiches "L'IA dans mon métier" (6 métiers, 3 cas d'usage chacun, tous reliés à une vraie fonctionnalité du site), simulateur coût/latence (mesure RÉELLE via `time.monotonic()` autour des appels Ollama, énergie explicitement labellisée "illustrative"), quiz de fin de brique + badges (2 questions/brique, ne bloque jamais la progression existante, juste une récompense optionnelle), assistant d'aide flottant (disponible sur toutes les pages via `App.tsx`).

**Leçon critique — l'assistant d'aide a hallucinée avant d'être ancré** : testé en conditions réelles avant publication (jamais supposé fonctionnel), le premier essai avec llama3.2:3b sans ancrage a défini RAG comme "Random Agent" — une pure invention, exactement le piège pédagogique que ce site enseigne par ailleurs. **Constructeur passé à 20 templates (2026-07-08)** : 10 nouveaux templates ajoutés, recomposant les mêmes 13 briques dans des combinaisons différentes autour de cas d'usage d'entreprise réels (support IT, RH onboarding, conformité+garde-fou, comptabilité, veille concurrentielle, CRM commercial, recrutement, traduction vérifiée, choix de modèle avant migration coût, contenu marketing avec garde-fou) plutôt que d'inventer de nouveaux types de nœuds. **Leçon de conception** : les templates n'ont pas besoin d'être structurellement uniques pour être pédagogiquement utiles — réutiliser un même enchaînement de nœuds (ex: modération→LLM, ou un nœud `verification`/`comparateur` seul) avec un cadrage métier différent illustre justement qu'un même pattern d'architecture s'applique à plusieurs contextes professionnels, ce qui est réaliste. Les templates sont servis dynamiquement via `/api/agents/templates` (pas de build-time constant côté frontend) donc un ajout de template ne nécessite qu'une sync backend + restart, jamais de rebuild frontend. Vérification systématique après ajout : script Python validant que chaque `node.type` existe dans `COMPOSANTS`, que chaque `edge` référence des `node.id` valides, et que chaque `exemple.valeurs` cible des `node.id` existants — a évité de découvrir un template cassé seulement au clic utilisateur. Point de vigilance data-flow découvert en écrivant ces templates : le nœud `verification` régénère son propre brouillon depuis `config.get("prompt")`, il n'exploite JAMAIS le `contexte` d'un nœud amont (donc chaîner `llm_agent → verification` ignorerait silencieusement le RAG) — uniquement utilisable en nœud terminal autonome, jamais après un autre nœud générateur.
